The mission is a state machine. SCAN spins in place to build the first map. EXPLORE drives to the most promising frontier. When an apple is seen three times we switch to APPROACH. If it isn't confirmed up close it was a false alarm and we go back to exploring; the same happens after a rescue while apples are still missing. Every new area gets another 360-degree look. Once two apples are confirmed, HOME drives back to the start and DONE stops the robot. A safety layer runs underneath every state.

One Python controller runs the whole loop. It senses with wheel encoders, the compass, the accelerometer, a 360-degree LiDAR and the camera. It thinks in four parts: localization, mapping, perception and planning. It acts through pure pursuit path following and a DWA local planner that turns the path into wheel speeds, with a safety and recovery layer on top.

Wheel odometry drifts because wheels slip. Heading comes from the compass, which we calibrate automatically against the encoders during the first spin. Position drift is fixed by scan matching: every few steps we try small shifts of the pose and keep the one where the LiDAR scan lands best on walls already in the map. In one test run that added up to 4.49 metres of correction over 247 fixes. The map itself is a 40 by 40 metre grid around the start, because we don't know the building's size in advance.

Plain frontier exploration just goes to the nearest unknown area. We added semantics: YOLO labels objects like dining tables, bowls and the fridge, and the LiDAR range along the box direction places them on the map. An object only counts after three sightings with a clear class vote. Each frontier then gets a score: travel distance minus a bonus for being near objects where fruit is usually kept. All class names are standard COCO classes, nothing specific to this apartment.

09 / 14

Red pixels alone are not enough: the fire extinguisher, cabinets and a red can are red too. Every red blob must pass six checks: it must be round, sit on the floor below the horizon, have the right pixel size for its distance, be fully in view, and not be part of a taller red object. Then we need three consistent sightings to approach, and two close-up confirmations within two meters before we count it. In our test runs there were no false alarms.

10 / 14

Driving has three layers. A* plans a global path on the map, with walls padded by the robot's radius, and we re-plan every 1.5 seconds. Pure pursuit picks a look-ahead point, and the DWA local planner simulates 90 short trajectories on a small costmap built only from the current LiDAR scan, so a walking person never leaves ghost obstacles behind. Underneath, the safety layer stops the robot if anything is closer than 20 centimeters, and a watchdog recovers if we stop making progress.

11 / 14

The LiDAR scans a flat plane about 15 centimetres up, so a 5 millimetre carpet edge, a decoy apple or a can lying on the floor is invisible to it. In testing our robot fell over on a carpet edge. So we added two more senses. First the camera: any small, strongly coloured object lying on the floor is located from where it touches the floor and marked as an obstacle after three sightings, before the robot touches it. Second the accelerometer, for what the camera can't see, like a carpet edge: a tilt over 6 degrees for 0.3 seconds makes the robot reverse until level and mark that spot. If it has to back off three times in 15 seconds, it turns toward the most open direction and picks a new goal, so it can't trap itself in a corner.

12 / 14

In our Webots test runs the robot found and confirmed both red apples, with no false alarms from the decoy apples or the red can. Testing also showed five real problems, and each one led to a fix: it fell over on a carpet edge, so we added tilt sensing; on some computers it missed the apple under the bathroom sink, so spots it failed at are now retried instead of ignored for good; it backed itself into a corner, so we limited back-offs and added an escape turn; it counted a found apple twice, so found apples are now stored from close-range sightings and remembered; and it kept reversing next to the start, so home now counts as reached within 0.6 metres when a wall is in the way.

Where could this go? We think a guide robot for blind people, like a robotic guide dog. Almost everything we built for search and rescue is what a guide robot needs. It explores places it has never mapped, so it could guide someone through an unfamiliar building. It dodges walking people in real time, which is what keeps a person safe in a crowd. Seeing and feeling obstacles below the LiDAR is the same problem as warning about steps, curbs and trip hazards. Finding apples with the camera becomes finding doors, empty seats or dropped keys. And remembering the way back to the start becomes leading the user home. What it would still need: a voice and haptic handle to talk to the person, a depth camera for stairs, planning for a person walking beside it, and outdoor navigation with GPS and crosswalks.
